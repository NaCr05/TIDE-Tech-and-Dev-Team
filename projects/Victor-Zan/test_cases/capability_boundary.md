# 系统能力边界说明

## 能稳定处理的场景

- [x] 数据结构算法题的答案评估（Pascal's Triangle 验证通过）
- [x] 代码正确性的静态分析（能识别硬编码限制、逻辑错误、边界条件问题）
- [x] 不同质量答案的有效区分（v2 Prompt 下 5 份答案得分 18-98，差距明显，且同 Bug 不同报告的答案成功区分）
- [x] 同一个提交反复评估结果趋于稳定（temperature=0.3）
- [x] 教师手动修改评分和评语并持久化保存
- [x] Mattermost Slash Command 双通道（发布 + 提交）
- [x] Bot 在关键节点主动推送通知

## 不能稳定处理的场景

- [ ] **代码运行验证**：AI 只做静态文本分析，不运行代码。无法判断代码是否真能通过 LeetCode 测试用例。一个看起来正确的代码可能有隐藏 Bug，AI 无法发现
- [ ] **严格数学证明**：数学归纳法、复杂度精确推导，AI 可能漏掉关键步骤或接受不严谨的论证
- [ ] **图表/绘图题**：AI 无法解析图片，只能评估附带的文字说明
- [ ] **长文本截断**：超过约 8K tokens 上下文时可能被截断
- [ ] **主观性极强的开放题**：评分标准难以统一，不同轮次可能有波动

## Agent 误判或不稳定输出的记录

| 现象 | 触发条件 | v2 改善情况 |
|------|---------|-----------|
| 整体评分偏低（v1 最优答案 83 分） | Prompt 对"实现与示例"要求过严 | ✅ 改为"代码本身就是实现"后提升到 98 |
| 相同 Bug 不同报告质量的答案得相同分 | 报告维度评分不够敏感 | ✅ Julia 44 vs Nina 28，已拉开 |
| 单个非致命 Bug 扣分偏重（扣 30/50） | 扣分规则未定义严重程度 | ⚠️ 仍扣 30 分，但总分因报告分提升而更合理 |
| 同一答案重复评估结果略有波动 | LLM 固有随机性 | temperature=0.3 已缓解，教师可手动调整 |

## 已知的 AI 误判案例

| 案例 | 学生答案特征 | AI 表现 | 处理方式 |
|------|------------|--------|---------|
| 代码 Bug 扣分重 | `min(numRows, 5)` 硬编码限制 | 代码扣 30/50 分，比例偏重 | 教师可通过"修改评估"手动调整 |
| 报告偏简但代码满分 | Ethan Liu 代码 50/50 但报告极简 | 总分 73，合理 | 无需处理 |
| 完全错误但有部分报告 | Student_Bad 代码全错但提了复杂度概念 | 给了 18 分而非 0 分 | 合理——部分报告内容仍有一定价值 |

## 系统架构限制

| 限制 | 说明 |
|------|------|
| 无用户认证 | 学生提交时手动输入用户名，无密码验证 |
| 无代码沙箱 | 无法安全运行学生提交的代码 |
| 无查重功能 | 不检测学生间抄袭 |
| 单线程评估 | 大量提交需逐个调用 AI，无并行处理 |
| 评估耗时 | 单次 3-10 秒（依赖 DeepSeek API） |

## v2 迭代总结（2026-07-23）

**迭代内容**：Prompt 评分校准 + Rubric 从 JSON 动态读取

**改善项**：
- 最高分从 83 → 98，进入合理区间
- Julia/Nina 从同分 27 → 44 vs 28，成功区分
- 评分分布 18-98，覆盖全部档次
- Rubric 不再硬编码，换作业只需换 JSON 文件

**仍存在的问题**：
- 代码单个 Bug 扣分仍略重（Non-blocking，可教师手动修正）
- 无法运行代码验证正确性（架构限制，需引入代码沙箱）
